- (decision) AD-1 Paradigm: hexagonal (ports and adapters) with a transactional application-service layer. NestJS modules map 1:1 to the PRD's feature groups. Binds all. Prevents two modules writing the same tables through their own repositories. Rule: a module reaches another module only through its application service; no cross-module repository or Prisma model access.
- (decision) AD-2 Sample is the design, Sample Piece is the physical copy. Binds FR-1..FR-5, FR-33. Prevents a quantity column on Sample, which cannot express "this specific piece came back stained" and kills piece history. Rule: availability, Holds, Loan Lines, Condition and Cases attach to sample_piece; catalogue attributes attach to sample; sample has no count column.
- (decision) AD-3 Loan Line is the unit of lending state. Binds FR-13, FR-15..FR-22. Prevents a loan-level returned flag, which is exactly the spreadsheet behaviour the product replaces. Rule: due date, return state, overdue and extension live on loan_line; loan has no due date and no stored status - its state is derived from its lines.
- (decision) AD-4 NFR-7 is a database constraint, not service code. Binds FR-7, FR-11, FR-15, NFR-1, NFR-7. Prevents a double-booked piece under concurrency. Rule: two partial unique indexes - one open loan_line per sample_piece WHERE resolved_at IS NULL, one active hold per sample_piece WHERE released_at IS NULL. Prisma schema cannot express partial indexes, so both live in hand-written SQL migrations that Prisma applies but does not generate.
- (decision) AD-5 Contended writes (reservation FR-7, handover FR-11, return FR-15) run as one transaction at READ COMMITTED, taking SELECT FOR UPDATE on candidate sample_piece rows in ascending piece-id order for a deterministic lock order, with AD-4's indexes as the backstop. Prevents lost updates and deadlock between two staff at the counter. Rule: on a unique violation the whole transaction rolls back and retries once, then returns a structured conflict naming the competing Kit or Loan. No partial success is ever committed.
- (decision) AD-6 Studio scoping lives in the data-access layer and read models are role-specific. Binds FR-4, FR-32, FR-37, NFR-9. Prevents a new endpoint that forgets the studio filter, and field-level redaction that leaks holder identity to Designers. Rule: every repository method touching Studio-owned data takes a required StudioScope argument; Designer responses are built from their own DTOs that have no holder field at all, rather than from a shared DTO with conditional fields.
- (decision) AD-7 History is append-only. Binds FR-40, NFR-8. Prevents an attributed fact being edited after a dispute starts. Rule: event tables carry created_at and created_by and no updated_at; the application database role is granted INSERT and SELECT only on them. Corrections are new superseding rows.
- (decision) AD-8 The showroom's calendar day governs lending time. Binds FR-8, FR-13, FR-20..FR-25. Prevents two modules computing overdue differently, and UTC drift making a piece overdue five hours early in Lahore. Rule: collection, expected-return and due dates are SQL DATE; everything else is timestamptz; overdue, due-soon and hold expiry are evaluated against current_date in Asia/Karachi, named once as a single shared function.
- (decision) AD-9 Photographs sit behind a PhotoStore port. Binds FR-17, NFR-9, PRD S6 privacy. Prevents binding the pilot to an unselected provider, and guessable public URLs. Rule: images never enter PostgreSQL; the port exposes put, signed-read and delete; reads are short-lived signed URLs minted only after the same authorisation check as the owning Case or Return Event; type and size caps are enforced server-side before the put.
- (decision) AD-10 Reminder drafting is a pure function, separate from delivery. Binds FR-24, FR-25, PRD S8.2. Prevents a future WhatsApp sender turning into a rewrite. Rule: draft text is produced by a pure function of (Studio, overdue Loan Lines, date) with no I/O and no dependency on any transport; suppression is its own studio_reminder record keyed by studio and showroom-local date, written by the act of generating a draft.
- (decision) AD-11 Availability is computed, never stored. Binds FR-3, FR-4, FR-7, NFR-2. Prevents a denormalised is_available flag that two modules maintain and drift. Rule: availability for a date is derived at query time from condition, active holds and open loan lines. At the stated volume (600 Samples, 1000 Pieces) this is a small indexed query and NFR-2's 2-second budget does not justify a cache.
- (decision) AD-12 Money is recorded, never moved. Binds FR-27, FR-28, PRD S6. Prevents a float amount, and a waiver that erases the number. Rule: replacement charge is an integer in minor units with an explicit ISO-4217 currency code; waiver is a separate nullable (waived_at, waived_by, waiver_reason) set on the Case that never overwrites amount; no payment, invoice, ledger or balance concept exists anywhere in the schema or the API.
- (decision) AD-13 Lending state changes are named operation endpoints, not field writes. Binds FR-7, FR-9, FR-11, FR-15, FR-18, FR-21, FR-29. Prevents a client flipping a status field and bypassing the rules. Rule: POST to a named sub-resource; no PATCH ever writes a state or status field.
- (decision) AD-14 The stack is provisional. Binds all. Prevents the team reading an unapproved proposal as an approved decision. Rule: AD-2, AD-3, AD-4, AD-7, AD-8, AD-11 and AD-12 are language-neutral and survive a move to Python or .NET; AD-1's module mapping and the Prisma migration mechanics in AD-4 are the only Node-specific calls and are the ones to revisit if the client chooses differently.

- (decision) AD-1 amended before distilling: the module mapping is NOT 1:1 with the PRD feature groups. Seven modules: catalogue, kits, lending, followup, cases, reporting, accounts.
- (decision) AD-15 One module owns each table; everyone else goes through its application service. Binds all. Prevents the two-owners hole that AD-1 alone leaves open - cases resolving a piece, and followup moving a due date, both write into another module's tables if unchecked. Rule: cases calls catalogue.retirePiece / catalogue.restorePiece; followup calls lending.applyExtension; reporting holds no write path at all and reads through owning-module query services.
